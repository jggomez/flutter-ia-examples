# 0004. Flutter State Management (Riverpod 3.x), Surface Navigation Stack, and Image Capture

- **Status**: accepted
- **Date**: 2026-10-21
- **Deciders**: flutter-architect

## Context

`apps/a2ui_snap_sell/mobile` is the third Flutter app in the `flutter-ai` monorepo, following `apps/rps_live` (ADR 0001) and `apps/event_llm_wiki` (ADR 0003). Both prior apps standardize on `flutter_riverpod ^3.4.3` with manual (non-codegen) `Notifier` / `AsyncNotifier` providers and a single DI composition root (`lib/ui/providers/repository_providers.dart`) whose providers throw `UnimplementedError` until overridden in `main.dart` or `ProviderScope(overrides: [...])`.

Specific to Snap & Sell:
1. The app wraps `genui`'s stateful runtime objects (`SurfaceController`, `A2uiTransportAdapter`, `Conversation`) and `genui_a2a`'s `A2uiAgentConnector`, all of which hold active `StreamController`s and `StreamSubscription`s that **must** be deterministically disposed.
2. The mobile app has **only one fixed screen** ("¿Qué quieres vender?" entry screen with camera/gallery buttons). Every subsequent screen is dynamically generated by the agent as an A2UI surface (`selling_step_1_detected`, optional `selling_step_2_followup`, `selling_step_3_preview`, `selling_step_4_published`, or `selling_unsupported`). Unlike the `verdure` sample (which hardcodes 5 `go_router` routes and maps fixed surface IDs to hardcoded screens), Snap & Sell must render *any* agent-generated surface dynamically without hardcoded form routes while still supporting Back navigation across completed steps.
3. The app needs still-photo capture from both the entry screen and the custom `PhotoRequest` catalog widget (for damage and odometer photos).

## Decision

1. **State Management — `flutter_riverpod ^3.4.3` Manual Providers**:
   - Inherit the monorepo convention: manual `Notifier` / `NotifierProvider` declarations (no `riverpod_annotation` / `riverpod_generator`), with `setState` reserved for purely local ephemeral widget state (e.g., image hover/press states or local slider drag state).
   - `lib/ui/providers/repository_providers.dart` is the single DI composition root exposing `sellingAgentRepositoryProvider` and `imageCaptureRepositoryProvider` (plus `snapSellCatalogProvider`), each throwing `UnimplementedError()` until overridden in `main.dart` or tests.
   - **Documented `.autoDispose` Exception (`sellingSessionViewModelProvider`)**: Following `event_llm_wiki` ADR 0003, `sellingSessionViewModelProvider` (`NotifierProvider<SellingSessionViewModel, SellingSessionState>`) is **not** `.autoDispose`. It owns the active multi-step selling session (`SurfaceController`, `Conversation`, `SellingAgentRepository` stream subscriptions, surface history stack, and loading/error state) across the entire selling flow and across native camera/gallery activity lifecycle transitions on Android (where launching the system camera can briefly pause/rebuild the host route). `ref.onDispose` and `SellingSessionViewModel.resetSession()` deterministically dispose the `Conversation`, `A2uiTransportAdapter`, `SurfaceController`, `A2uiAgentConnector`, and all `StreamSubscription`s.
2. **Surface Navigation — Single Host with Reactive Surface History Stack (No Hardcoded Form Routes)**:
   - Maintain `List<String> surfaceHistory` and `int activeSurfaceIndex` inside `SellingSessionState`:
     - When `surfaceHistory.isEmpty` and not loading an initial upload, render the fixed `EntryScreen` ("¿Qué quieres vender?").
     - When `ConversationSurfaceAdded(surfaceId, definition)` fires for a new `surfaceId`, append `surfaceId` to `surfaceHistory` and advance `activeSurfaceIndex = surfaceHistory.length - 1`.
     - When `ConversationComponentsUpdated(surfaceId, definition)` fires for an existing `surfaceId`, keep `surfaceHistory` intact and switch `activeSurfaceIndex` to that `surfaceId`'s index (supporting in-place validation errors or odometer OCR pre-fills without duplicating steps).
     - Wrap `DynamicSurfaceHostScreen` in a `PopScope`: hardware/app-bar Back decrements `activeSurfaceIndex` if `activeSurfaceIndex > 0`, or prompts to confirm resetting the session (`resetSession()`) when at index `0`.
3. **Image Capture — `image_picker ^1.2.4` behind `ImageCaptureRepository`**:
   - Use `image_picker ^1.2.4` (wrapped by a thin, untested `ImagePickerService` in `lib/data/services/image_picker_service.dart` and `ImageCaptureRepositoryImpl` in `lib/data/repositories/image_capture_repository_impl.dart`) for both the entry screen and the `PhotoRequest` custom catalog component.
   - Configure `maxWidth: 1280, maxHeight: 1280, imageQuality: 80` on all `pickImage` calls.
4. **Error, Offline, and Loading States**:
   - `SellingSessionState` models explicit `SellingFlowStatus` (`idle`, `capturingImage`, `uploadingAndAnalyzing`, `renderingSurface`, `submittingAction`, `error`) plus `String? statusMessage` and `SellingFailure? failure` (with retryable last message/action).
   - While `isWaiting` is true on `Conversation` (or `status` is `uploadingAndAnalyzing` / `submittingAction`), display a non-blocking overlay/banner with contextual progress text streamed from A2A `TaskState.working` updates (e.g., *"Analizando foto con Gemini..."*, *"Calculando rango de precio sugerido..."*) and a Cancel button wired to `CancellationSignal`.

## Alternatives considered

- **`go_router` with hardcoded routes per selling step (as in `verdure`)** — rejected because Snap & Sell's core product requirement is that the mobile app has **no hardcoded form screens** after the entry screen; the agent dynamically determines which surfaces to create (`selling_unsupported`, `selling_step_1_detected`, conditional `selling_step_2_followup`, `selling_step_3_preview`, `selling_step_4_published`).
- **`camera ^0.12.1` live preview plugin (as in `rps_live`)** — rejected because Snap & Sell captures discrete still photos (item photo, damage photo, odometer photo) rather than 30fps tensor streams; `image_picker` delegates to the native OS camera/gallery sheet, handles EXIF orientation and 1280px JPEG resizing natively, and avoids holding a hardware camera controller open alongside network streaming.
- **Riverpod codegen (`riverpod_annotation` / `riverpod_generator`)** — rejected because `context/memory/conventions.md` mandates manual Riverpod 3.x providers without codegen across the monorepo.

## Consequences

- **Positive**: 100% consistent with `rps_live` and `event_llm_wiki` architecture and testing conventions (`ProviderScope(overrides: [...])` with fakes).
- **Positive**: Zero hardcoded form screens; any new surface emitted by the agent renders immediately inside `DynamicSurfaceHostScreen` with full back-stack support.
- **Positive**: Deterministic `.dispose()` chain prevents memory leaks across `SurfaceController`, `Conversation`, `A2uiTransportAdapter`, and `A2uiAgentConnector`.
- **Trade-off**: Custom `PhotoRequest` widget needs access to the session's `uploadFollowupPhoto` command; we inject an action callback into ` buildSnapSellCatalog(onPhotoRequest: ...)` via Riverpod so `PhotoRequest` remains decoupled from `data/` services.

## Compliance

`flutter-reviewer` checks:
- No `go_router`, `flutter_bloc`, `provider`, `signals`, or `riverpod_annotation` in `mobile/pubspec.yaml`.
- `mobile/lib/ui/**` never imports `package:genui_a2a`, `package:image_picker`, or `mobile/lib/data/**` except in `lib/ui/providers/repository_providers.dart` / `main.dart`.
- `SellingSessionViewModel` registers `ref.onDispose` that disposes `Conversation`, `SurfaceController`, `A2uiTransportAdapter`, `A2uiAgentConnector` (via repository `dispose()`), and cancels all `StreamSubscription`s.
- All `async` UI handlers check `if (!context.mounted) return;` before using `BuildContext` across an `await`.
- A regression test in `mobile/test/regression/session_lifecycle_regression_test.dart` verifies that `resetSession()` and provider disposal release all streams and reset surfaces cleanly.
